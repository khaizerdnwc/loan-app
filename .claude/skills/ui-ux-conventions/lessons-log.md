## ui-ux-20261128-validator-message-in-words

Lane D batch 2 (PRD #30) added the new-customer inputs to the intake Review draft dialog. A bad "Months employed" comes back from the global ValidationPipe as "newCustomer.employmentMonths must not be less than 0", and a bad obligations figure as "monthlyObligations must be a decimal string with at most 2 decimals". apps/api/src/problem.filter.ts:63-72 passes the class-validator text through as the field error, and the dialog shows it under the input. The Vitest case (apps/backoffice/test/intake.test.tsx:278-308) asserts that raw text as the expected screen. Why: Engineering Standard 6 says error messages are useful, in words a loan officer understands. A property path is not such words. Fix shape: give each DTO decorator an officer-worded `message` ("Enter the months employed as a whole number from 0 to 600"), or have the problem filter map known constraints to words by field. A lint rule requiring `message` on every decorator would flag about 100 existing decorators across four DTO files, so the fix belongs in one place (the filter) or a planned sweep. Found reviewing lane D batch 2 on 2026-11-28. Nearest deterministic alternative: an API e2e assertion that no field error message starts with its own field path.

## ui-ux-20261128-field-error-needs-its-field

The intake Review draft dialog (lane D batch 1, PRD #30) renders the "Government ID, last 4 digits" input only when OCR could not read the ID. The API's no-customer-match refusal puts its guidance ("Capture the customer first (New application, New or walk-in customer) with this name, birth date and ID, then confirm the draft again") in a field error on `governmentIdLast4`. A draft flagged NO_CUSTOMER_MATCH always has the ID read (intake-rules.ts flags no-match only when the ID is present), so the input is hidden and `fieldErrorsOf` drops the one sentence that tells the officer what to do; they see only "No customer record matches this draft." The Vitest case covered only the ID-missing branch, where the input exists. Why: Engineering Standard 6 (useful error messages); the API wrote the remedy and the screen threw it away. Fix shape: show field errors with no rendered input in the dialog's error callout (or render the field read-only), and test the no-match draft with the ID read. Found reviewing lane D batch 1 on 2026-11-28. Nearest deterministic alternative: a component test per conditional field that mocks the API's field error on a draft where the field is hidden and asserts the message is visible.

## ui-ux-20261128-no-figure-below-minimum

The Model governance drift card pills "Not enough decisions" (fewer than 30 scored decisions in a window) yet the sentence beside it still prints "Population stability index 0.4123 (under 0.10 stable, 0.25 and over significant)". The API computes PSI on any non-empty windows and only withholds the status. A compliance reader sees a figure in the "significant" range next to a pill saying there is nothing to judge, and the figure is the one that gets quoted. Why: Engineering Standard 6 (understandable states); a statistic below its minimum sample is noise. Fix shape: under INSUFFICIENT_DATA show "PSI not computed: baseline N, recent M of the 30 needed per window" (or the API sends psi null). Found reviewing lane C batch 3 on 2026-11-28. Nearest deterministic alternative: a component test rendering DriftMonitor with status INSUFFICIENT_DATA that asserts no PSI figure and the counts.

## ui-ux-20261128-no-engine-version-table

Gate: house/no-engine-version-literal

decision-panel.tsx kept a table of score-band edges keyed by rule-set version ("RS-PL-1", "RS-PL-2"). When RS-PL-3 went live, every new decision lost its score band: the panel quietly fell back to the rule text, no unit test noticed, and only the F1/F2 browser journeys caught it at merge (2026-11-28). ## ui-ux-20261128-engine-figure-says-basis

RS-PL-3 adds the engine's affordable amount to the decision record and the decision panel labels it "Recommended amount". On the same screen "Recommend a decision" is the loan officer's regulated step, and the approver reads "the recommendation" as the officer's. The engine returns "0.00" when nothing is affordable, which the panel shows as "Recommended amount ₱0.00", without words: it reads like an error or an offer of nothing. Why: Engineering Standard 6 (understandable states) and the rule that only an approved offer is an offer. Fix shape: name it as the engine's ("Affordable amount (engine)"), say it is indicative and not an offer, and turn the zero into a sentence ("Nothing is affordable at this grade's rate within the 50% debt-service limit"). Found reviewing lane C batch 2 on 2026-11-28. Nearest deterministic alternative: a component test rendering the panel with recommendedAmount "0.00" that asserts the sentence and no "₱0.00".

## ui-ux-20261128-unavailable-says-why

When a provider could not answer and a field is shown as "Unavailable", the same card says which provider could not answer and what that means for the case (it still proceeds; the figure is quoted again later, or never). Why: on the approved-terms card (BK/#13, 2026-11-28) the monthly instalment read "Unavailable" while the caption under it still said "instalment quoted by core banking (simulated)" — the screen contradicted itself and an officer could not tell whether the offer or the booking was blocked (Engineering Standard 6: understandable pending states). The indicative-repayment box on the same change did it right: "Core banking could not quote it just now. This does not affect saving or submitting the application." Nearest deterministic alternative: a component test that renders the panel with the value null and asserts the explanatory sentence and the absence of the "quoted by" caption.
## ui-ux-20261128-dialog-offers-only-accepted-choices

The Recommend dialog opens on "Approve as requested" for every REVIEW case. With automation off, in shadow or under the kill switch (PRD §7.5), a case whose policy knockout failed (a sanctions match, an existing default, age outside policy) no longer auto-declines: it is referred to a loan officer, and CasesService.recommend refuses anything but a decline with 409. The officer picks the default, writes a rationale, confirms, and only then learns the case could only ever be declined. The case's `allowedActions` lists RECOMMEND as enabled with no hint that its choices are narrowed. Why it matters: Engineering Standard 6 (confirmation states what will happen) and the house convention that a button a role cannot use is hidden or disabled with a visible reason. Found reviewing the automation-modes batch (Lane C) on 2026-11-28. Nearest deterministic alternative: the API says which recommendation types it accepts for the case (e.g. on the RECOMMEND availability) and a Vitest case renders the dialog for a knockout case and asserts Decline is the only enabled option; an e2e step under shadow mode with a knockout persona.

## ui-ux-20261128-no-reason-code-mirror

Gate: house/no-reason-code-literal

actions-panel.tsx decided "referred because a provider could not answer" by testing the decision's reason codes for R10 or R13. The automation batch added the fraud check and its outage code R17; the API's predicate (DecisionService.unavailableProvider) learned it, the screen did not, so on a fraud-check outage the API offers "Decide again" while the next-action line says "Referred: a loan officer reviews the evidence and recommends a decision". Reason codes are the engine's vocabulary and grow with each rule set; what a case waits for is the API's to say (AGENTS.md §2.1). Found reviewing Lane C batch 1 on 2026-11-28. A string literal that is exactly a reason code in web code is now a lint error.

## ui-ux-20261127-dialog-follows-refreshed-case

When a refused action re-reads the case (CHANGES_ON_REFUSAL in actions-panel.tsx) and the confirmation dialog stays open to show the error, the dialog must follow the refreshed case: re-title it to the action the new status lists (Approve booking becomes Retry booking on BOOKING_FAILED) or close it and show the error inline on the panel. Why: the header says "Booking failed" and the panel offers "Retry booking" while the still-open dialog asks "Approve this booking?" with an "Approve booking" button; the next click is in fact a retry under a different name, and the supervisor confirms something the screen no longer describes (Engineering Standard 6: understandable states, confirmation states what will happen). Found reviewing the B-5 re-read change on 2026-11-27. Nearest deterministic alternative: a Vitest case that re-renders ActionsPanel with the refreshed detail and asserts the dialog's confirm label.

Widened 2026-11-28 to `components/compliance/**`: the AML escalation actions (escalation-actions.tsx) keep the Acknowledge / Close dialog open on an INVALID_STATE refusal ("already acknowledged" / "already closed" by a colleague) without re-reading the escalation, so the dialog still offers a step the escalation no longer allows. Same remedy: on that refusal re-read the escalation and close the dialog, or re-title it to what the new status offers.
